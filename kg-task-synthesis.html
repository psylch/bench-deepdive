01Kimi K3 4.2.2

做法（原文）：建一张「自我演化、层级组织」的知识图谱，覆盖知识密集和编程领域。

  • 结构是 DAG，人只给粗种子节点，例如 CS/AI、生物医学、编程、数学、物理、化学、人文。
  • 每个节点交给一个 agent，先多轮联网搜索把概念查清，再加更细的子概念；加之前先在图里找相同或相近的节点复用；边永远从粗指向细；新节点再分给新 agent，直到 agent 判断概念「足够原子」。
  • 造题三步：按领域和题型比例在不同粒度采样关键词（可多个相关关键词一起抽）→ 关键词拼上祖先节点的上下文作为检索词，去网上取公开论文、博客、代码仓库 → 合成 agent 按指定题型（编程、知识、视觉等）出题。

未公开：节点数、层数、每类题量、合成题的校验方法。

02Simula（Google）

  • 全称：Reasoning-Driven Synthetic Data Generation and Evaluation
  • 机构 / 时间：Google、Google DeepMind、EPFL；TMLR 2026-03，arXiv 2026-03-31
  • 链接：arXiv 2603.29791；OpenReview。社区复现 Mercity-AI/Simula（6⭐，不是官方代码）

一、问题

原文的例子：要造一个「关于猫的故事」数据集，描述本身是欠定的，没法穷举所有符合描述的数据集，所以也无法回答「我造出来的这批数据覆盖了哪一块」。随机采样没有全局覆盖的概念；用分类树就能把覆盖变成可以度量、可以规划的东西。

论文把「好数据」拆成三个维度：

  • 质量：例如分类器训练数据应包含被部分遮挡或在阴影里的猫；
  • 复杂度；
  • 多样性，又分全局和局部。全局指是否覆盖了主要因子（猫的品种、颜色、环境），局部指同一个因子组合下有多少种不同演绎（一只红猫躺在沙发上的不同写法）。

二、分类树怎么建

  1. 找变化因子：推理模型根据用户描述 y 和 / 或一份目标分布样本 S 提出若干变化因子，可以由模型或人接受或拒绝。
  2. 每个因子展开成一棵树：按用户指定的深度广度优先展开。例子：猫 → domestic → shorthair → British shorthair。
  3. 防止「漏枝」：原文图 1 专门画了逐层丢失覆盖的情况（例如漏掉「大型野生猫」这一支）。解决办法是每个节点交替做三步： - Best-of-N 提案：给定节点、它的祖先和兄弟节点，让模型提 N 次子节点，扩大候选覆盖面、照顾边缘情况； - 批评：另一次调用让模型当批评者，对候选做增、删、合并、编辑，提升完整性、合理性和具体性（利用生成和批评之间的能力差）； - 层级规划（可选）：一层全部生成完后，先为下一层写一份「计划」，保证并行展开时同一层的粒度一致。

三、怎么采样

  • 采样策略（管全局多样性）：模型先制定策略，规定哪些树一起采、各占多少权重，把互相兼容的子集分到一组，避免不合逻辑的组合。原文例子：「儿童内容」策略只组合简单主题和适龄格式，排除成人主题，就不会生成给幼儿看的恐怖小说。
  • 从节点到 meta prompt：采到的节点相当于数据点的「需求」，例如 {house cat, poem, travel enthusiast} 变成「Compose an exciting haiku about a house cat who goes on an adventure.」
  • 覆盖比例的算法：要 100 条数据而有 200 个独特节点组合，全局覆盖率只有 0.5；要 800 条，每个组合可以出 4 个 meta prompt，覆盖全部空间，并逐步提高局部多样性。
  • 防模式坍缩：每个组合的 prompt 一多就容易越来越像，所以一次生成多个再抽取；样本量很大时改成把之前的生成结果放进上下文，顺序生成。
  • 加难（complexification）：按用户设定的比例 c，让模型在满足原有需求的前提下提高 prompt 和输出的复杂度。

四、验证

  • 逐条批评：把生成时用的 meta prompt 给模型，要求给出解释和二元判断。例如检查那首俳句里的猫是不是家猫、是不是俳句、有没有冒险。
  • 双重批评：对有标准答案的任务（分类、选择题），分别独立评估「是否正确」和「是否错误」，以减轻顺从偏差。
  • 判断为否就拒绝，或根据解释自动修改后再评一次。
  • 原文图 3 显示，模型给出的复杂度和人工判断一致，被拒绝的样本普遍更难。

五、实验

  • 设置：学生模型 Gemma 3 4B，教师 Gemini 2.5 Flash（非思考模式）。GSM8k、Global MMLU 用预训练版起步，较新的冷门数据集 CTI-MCQ、CTI-RCM、LEXam 用指令版。每个配置用不同随机种子做 10 次 LoRA 微调，报告均值和 95% 置信区间。
  • 复杂度消融：按每个分类节点内的复杂度分数切成低（后 40%）、高（前 40%）、全部三组。
  • 结论：复杂度和多样性对下游的影响取决于领域、模型、用途和规模，没有「银弹」。完整 Simula 训出的学生模型持续更好，换优化器（Muon）也成立。
  • 成本：Simula 每个数据点的推理调用最多是基线的 5 倍；但原文认为，算上训练成本，数据量更小、质量更高反而更省。

03STEPS

  • 全称：Towards Compositional Generalization of LLMs via Skill Taxonomy Guided Data Synthesis（Skill Taxonomy–guided Entropy-based Post-training data Synthesis）
  • 机构 / 时间：北航、智源、北理工、中科院计算所；arXiv 2026-01
  • 链接：arXiv 2601.03676；OpenReview；论文给的代码地址 github.com/STEPS 不是有效仓库

一、问题

真实语料里，复杂的技能组合服从长尾的幂律分布，多个技能需要协同时模型性能会急剧下降。以往的随机或启发式技能混合（例如 Instruct-SkillMix）不考虑技能之间的层级关系，组合出来的指令语义不连贯。

二、技能树怎么建：自底向上，按结构熵归并

  1. 给每条真实指令打上一组技能标签，建技能共现图：节点是原子技能，边权是两个技能出现在同一条数据里的概率。
  2. 每个原子技能先当作一个单独的社区，也就是树的叶子。
  3. 每步合并能让结构熵下降最多的两个社区，合并后的社区作为新的内部节点挂在树上。直觉是：好的层级应该让高权重的共现边尽量落在局部组内部，而不是跨组。
  4. 这棵树不是人画的，也不是 LLM 拍脑袋给的，而是从真实数据的共现统计里「算」出来的。

未公开：原子技能总数和树的层数。

三、怎么采样：最大化边际结构信息

  • 选 k 个技能组合时，把联合结构熵按链式法则拆成条件项。第 i 个技能的「边际结构信息」取决于它和已选技能在树上的最近公共祖先：离得越远、所在区域越松散，贡献越大。
  • 贪心选择：从一个初始技能出发，每步选边际信息最大的那个。
  • 原文的意思是：组合局限在一小块区域里是冗余的，跨区域组合才有新信息，但又要留在同一个连贯的层级语境里。
  • 还设了一个「甜点区」约束来限定组合范围（RQ4 专门检验）。

四、怎么出题

把选中的技能组合和对应的参考样例一起给 LLM，让它生成同时体现这些技能的新指令和解答。附录给了样例对话，例如表 5「金库初始化里的对象操作 + 数学优化」，表 6「并发金融分析手机 App 的架构与实现指南」。

验证：论文没有单独的题目质量过滤环节。

一、分类树怎么建

四个维度，每个领域下有预定义的取值池：

  • 领域（人工策划，是入口）：附录 Table 3 列了软件工程、调试、系统管理、文件操作、安全、数据处理、数据查询、数据科学、科学计算等。例如「文件操作」的定义是从二进制格式提取结构化内容、大规模文本编辑、修复损坏的容器，以文件系统和格式层面的推理为主。
  • 技能类型：算法、系统、配置、密码学……
  • 能力（要激发的推理行为）：探索、错误恢复、约束满足、长程规划……
  • 工程形态：写新功能、调试、DevOps、重构……

这不是一棵会长的树，而是人定的多维网格。原文附录给了完整取值；节点总数未汇总。

二、采样与取素材

  1. 每次在各维度上各抽一个取值，组成锚点；围绕锚点头脑风暴任务点子，要求「技能层面多样，而不只是话题表面多样」。
  2. 点子按创意、技术依据、可行性打分，低分直接淘汰（这一步去掉 30%）。
  3. 证据引导精修：专门的 research agent 去搜仓库、文档、issue 讨论、教程和用例，把证据逐步写进任务规格，落到具体工具、真实约束、已知故障模式和明确的输入输出约定上；找不到依据的候选（例如要求不存在的工具或约束互相冲突）丢弃。
  4. 编译成蓝图：面向用户的指令、只给参考解法用的内部提示（hint）、环境清单。

原文样例（图 1）：

  • 指令：写一个 CLI 程序 python3 /app/metronome_beats.py VIDEO.mp4，检测节拍器摆锤的左右极值，输出 WebVTT。
  • 内部 hint：跟踪饱和色的摆锤色块，允许竖直移动，不要硬编码颜色和 y 坐标，同侧极值去抖 ≥8 帧，用 cv2 读 fps 和尺寸。
  • 环境：合成不同节奏、颜色、位置的节拍器视频，加上收集的真实视频；运行环境 python:3.11-slim + OpenCV + NumPy。

三、环境实现

按清单从公开来源取素材（源码仓库、文档、数据集、配置文件、服务日志），再做适配：统一格式、注入受控故障、调参数；找不到合适素材就从零合成「已知真值」的变体。打包成固定版本的 Docker 镜像，跑冒烟测试（依赖安装、服务启动、目录结构、端到端可达），不通过就丢弃。

四、验证与过滤（淘汰率全部公开）

  • 测试构造：测试 agent 生成测试，再按正确性、确定性、边界覆盖三类 rubric 反复修改。校准实验：同一流程给 Terminal-Bench 2 的 89 道题出测试，官方解法通过率 91%；用 Codex（GPT-5.4）做语义比对，和官方测试的吻合度为 88%。
  • 带提示过滤：带 hint 的解题 agent 必须成功，不带 hint 的另一个 agent 必须失败，两者都满足才保留，去掉太容易的题。
  • fail-to-pass：测试在初始环境必须失败，跑完参考解法后必须通过。

各阶段保留率：点子 100% → 筛点子后 70.0% → 蓝图校验后 56.0% → 环境构建后 42.0% → fail-to-pass 后 33.6%。也就是约三分之二被淘汰。

蓝图 rubric 审核让通过率从 72% 升到 91%（人工评审），从 75% 升到 93%（LLM 评审）。

五、实验与消融

  • 主结果：6K 条轨迹微调 Qwen3-32B，Terminal-Bench 2.0 达 33.4%（avg@4）；8B 从 2.5% 到 10.9%，14B 从 4.0% 到 23.0%。
  • 同等数据量对比（6K 轨迹，Qwen3-32B）：TerminalTraj 18.0，Nemotron 28.9，CLI-Universe 33.4。
  • 证据精修的效果：解题轮数从 5.34 涨到 18.43（3.45 倍），通过率从 68.2% 降到 54.9%，说明题目真的变难了，而不只是变长。
  • 组件消融（1K 子集，满配 26.7）：去掉素材策略 20.5（−6.2），去掉 query rubric 23.3（−3.4），去掉测试 rubric 22.8（−3.9）。
  • 轨迹选择：只用 6K 条成功轨迹 33.4，全部 10K 条都用只有 28.2。
  • 教师模型：Kimi-K2.6 33.4，DeepSeek-V4-Pro 31.2。
  • 未公开：单题成本和 GPU 用量。

六、局限（原文）

数据质量的上限受底层模型能力约束；和最强的闭源模型仍有明显差距；没试过 RL 和更大的基座；数据只有 6K 条。

七、与 K3 4.2.2 对照

  • 相同：「采样 → 联网查真实材料 → 出题」三步几乎一样，研究 agent 的检索对象（仓库、文档、issue）和 K3 的「论文、博客、代码仓库」高度重合。
  • 不同：分类不是 agent 长出来的，而是人定的四维网格；K3 只写到出题，CLI-Universe 把出题之后的环境、测试、hint 过滤和 fail-to-pass 全写了，并给出每一步的淘汰率。

05Nemotron-Terminal（NVIDIA）

  • 全称：On Data Engineering for Scaling LLM Terminal Capabilities
  • 机构 / 时间：NVIDIA；arXiv 2026-02-24
  • 链接：arXiv 2602.21193；模型和数据 HF nemotron-terminal

一、两路数据

1. 数据集改写（不需要 LLM 参与）

把现有 prompt 直接套进 Terminus 2 的系统模板，再按数据类型加指令后缀。SWE prompt 里提到的每个代码文件都在环境里建出来。没有测试用例。

来源 原始规模 改写后
数学 — 162,692 条

2. 合成任务 Terminal-Task-Gen

  • 基于种子：拿相邻领域的现成题目（科学计算、算法题等）当灵感，由 LLM 改写成自包含的终端任务。种子记录包含题目描述、可选的领域标签、可选的参考解法；参考解法只用来生成测试期望，不给 agent 看。改写时要求补上装包、从指定路径读输入、写到指定位置等工程要求，并生成真实的输入数据。
  • 基于原子技能分类：这是和本页主题相关的部分，见下。

二、原子技能分类

  • 9 个领域：数据处理、数据查询、数据科学、调试、依赖管理、文件操作、科学计算、安全、软件工程。每个领域有一套专门的生成 prompt，例如数据科学的 prompt 偏向统计分析和数据变换，安全的 prompt 强调密码操作和访问控制验证。
  • 6 类原子技能：
  • 算法：图遍历、约束满足、回溯搜索
  • 系统：文件 I/O、进程管理、网络配置
  • 数据处理：解析、序列化、变换流水线
  • 数学：数值积分、统计建模
  • 测试：验证、基准测试
  • Web 与安全：HTTP、认证、漏洞分析
  • 附录表 10 的示例技能：
  • 「构造利用载荷绕过认证并识别漏洞」
  • 「用 BFS/DFS 做依赖解析」
  • 「带编码和校验地解析 JSON/XML/CSV」
  • 「通过约束分析解决包依赖冲突」
  • 「计算离散概率分布之间的距离」
  • 组合：每个任务通常组合 3–5 个技能，prompt 强调要发明新场景，以最大化多样性和覆盖面。
  • 分类由人策划，再由 LLM 扩展和重组；不是 agent 长出来的树。

三、过滤

  • 去污染：和 Terminal-Bench 2.0 测试题有 14-gram 重合的 prompt 删掉。
  • 质量过滤：去掉身份泄露和含中文字符的回复。
  • 轨迹过滤：试过只保留完整轨迹、只保留通过测试的轨迹两种做法（结论见下）。
  • 教师模型是 DeepSeek-V3.2。

四、实验与消融（Qwen3-8B，Terminal-Bench 2.0）

数据 条数 TB2.0
只用数学改写 162,692 5.39
只用代码改写 31,960 6.29

  • 轨迹过滤反而有害：合成任务不过滤 12.4，只保留完整轨迹 6.74，只保留成功轨迹 5.06。原文解释，严格过滤丢掉一半以上的数据，而失败轨迹能让模型见到真实的报错状态和恢复过程。

  • 训练成本：8B 和 14B 用 32 张 GPU，32B 用 128 张 GPU。

五、和 CLI-Universe 的结论相反

CLI-Universe 发现只用 6K 成功轨迹（33.4）比全部 10K（28.2）好；Nemotron-Terminal 发现不过滤最好。两者的差别在于题目本身有没有经过严格验证：CLI-Universe 的题经过 fail-to-pass 检查，Nemotron 的合成任务没有。面试时可以拿来讨论「过滤应该放在题目端还是轨迹端」。

六、局限（原文结论）

只做了 SFT，RL 留作下一步。

七、与 K3 4.2.2 对照

  • 相同：都按「领域 × 技能」的分类控制覆盖面，用 LLM 扩写。
  • 不同：Nemotron 的分类是平的两层（领域 → 技能类型），没有联网取素材，题目来自 LLM 发明的新场景。

06LongCrafter

  • 全称：LongCrafter: Towards Diverse Long-Context Understanding via Evidence-Graph-Guided Instruction Synthesis
  • 机构 / 时间：中国科学院大学、中科院自动化所；arXiv 2026-07，v2 2026-08-03
  • 链接：arXiv 2607.06160；代码未公开

一、任务分类树（人工构建）

  • 第一层：只靠局部证据就能做的任务（局部 / 浅层），和需要整合全局分散证据的任务（全局 / 深层）。
  • 往下：按所需能力分组，最后得到 32 种细粒度任务类型，覆盖单文档和多文档两种设置。例如全局摘要、文档内多跳推理、全局时间线推理、代码理解。
  • 这棵树是之后所有阶段的「全局生成先验」。

二、取素材：按任务配上下文

  1. 建语料：从多种网页来源收集文档；按来源做过滤（去掉解析失败、编码错误、来源不明、重复的文档），再按样本做过滤。
  2. 粗匹配：先按来源对应候选任务类型，例如代码文档对应代码理解任务。
  3. 单文档：每篇文档匹配一个适合的单文档任务，均匀切块。
  4. 多文档：把文档当成根文档；LLM 按根文档和目标任务类型生成检索词，用 BM25 + 稠密检索的混合策略找补充文档，再由 LLM 同时按相关性和多样性筛选，保证主题相关但不重复。

三、证据约束图（核心）

  1. 穷举抽取：对每个块，参照全文，LLM 抽出和任务相关的候选证据片段，记录原文片段、位置和任务必需的关键信息。先多抽，避免漏掉那些只在跨块推理里才关键的证据。
  2. 按任务建图：在完整上下文上做一次全局推理，从候选里选出「对这个任务类型既必要又充分」的最小证据集合作为节点。边是有向的跨段依赖，包括时间、因果、指代。

原文图 3 示例（全局时间线推理）：

  • 节点 1：「A 收购 B，签约」（2021-03-15）
  • 节点 2：「B 以 A 旗下名义推出新产品线」（2021-09-08）
  • 节点 3：「A 报告 40% 收入增长归因于 B」（2022-06-30）
  • 边：1→2（+6 个月，促成产品扩张），2→3（+9 个月，带来增长），1→3（根因）
  • 约束：至少三个时间点

四、出题

根据上下文和证据图生成指令；回答要逐步引用段落证据，例如「第 1 段写到……说明收购发生在 2021-03-15」。

五、验证

  • 没有可执行验证；用 GPT-5 给指令难度打分，用 GPT-5 判答案对错。
  • 抽 500 条（每个数据集 100 条）做人机一致性检验，确认 LLM 评审可靠。
  • 未公开：最终数据量、淘汰率、成本。

07BenchBench（评测侧）

  • 全称：BenchBench: Benchmarking Automated Benchmark Generation
  • 机构 / 时间：南洋理工；KDD 2026，arXiv 2026-03-21
  • 链接：arXiv 2603.20807；论文给的仓库 github.com/koanatakiyo/BenchBench 目前 404

一、出发点

静态 benchmark 会饱和、会被污染、更新成本高。论文认为评测不应该只看模型答题答得多好，还要看它出题出得多好：出题要选对考什么技能、控制难度和格式、预判失败模式，还要能区分模型，同时不能夹带对某个模型家族有利的痕迹。

二、「领域卡片」：从种子 benchmark 抽出来的分类树

种子是 4 个 benchmark：CSBench（计算机）、WeMath（数学）、MedXpertQA（医学）、ToMBench（心智理论），一共做了 9 个变体，含多语言和多模态。

每个变体抽一张领域卡片，内容包括：

  • 粗粒度的主题 / 子领域本体，论文叫「super-parents」；
  • 代表性术语和约束；
  • 模态和语言要求。多模态卡片还要写清什么算有效的图像引用。

生成时只依据卡片，不直接复用种子题。卡片以 YAML 发布，附层级图。

三、按配额出题

每个设计者模型按四种配额生成题集：

  • super-parent 覆盖；
  • 题型：单选、多选……判断；
  • 声明难度 L1–L5，从回忆 / 单步到多步多概念；
  • 标准题和对抗题。对抗指「专门瞄准失败模式」，和难度正交，可以浅但刁钻。

分批生成：每批之后计算配额缺口，针对缺口补一批（top-up），直到覆盖达标。每道题必须带完整的 schema 字段，方便确定性审计。

设计者：gpt-5-mini、gemini-2.5-flash、deepseek-chat、qwen3-next-80b-a3b-instruct、doubao-seed-1.6-flash、llama-4-maverick；CSBench-EN 额外加 claude-sonnet-4.5 和 grok-4.1-fast。

四、验证与过滤

答题评审组：10 个模型（gpt-5-mini、gpt-4.1-mini、gemini-2.5/2.0-flash、deepseek-v3.2-chat、qwen3-next-80b、qwen3-vl-flash、doubao-seed-1.6-flash、llama-4-maverick、llama-3.3-70b）。

打分顺序：

  1. 选择题精确匹配；
  2. 短答案做数值或符号匹配；
  3. 其余用 rubric 评审（评审模型是 gemini-2.5-pro）；
  4. 无法验证或题目本身有问题的标记为 skip_core。

约 22% 的有效回答需要 rubric 评审。

另有一个质量评审模型，专门标出歧义题、标准答案错误、违反约束的题；schema 检查不过或被标记的题都排除出核心集。

四类指标：

  • 有效性（非核心率）；
  • 是否符合规格（领域、格式、难度分布和目标之间的 JS 散度，声明难度和实际难度的相关性，语言和图像约束的遵守率）；
  • 诊断价值（难度、区分度、排名一致性）；
  • 交互偏差（设计者是否偏向自己或同家族的模型）。

五、规模与结论

  • 生成 16.7K 题，过滤后约 15K 核心题，约 152K 条打分记录。
  • 出题能力和答题能力只中等相关（Spearman ρ≈0.37）。
  • 无效率和区分度负相关（Pearson r≈−0.62）：设计者产出的无效题越多，整套题的区分度越差。
  • 偏向自己或同家族模型的程度因题集而异。

未公开：单题成本。

六、与 K3 4.2.2 对照

  • 相同：「先有覆盖地图，再按配额出题」；BenchBench 多了按缺口补题的闭环。
  • 不同：卡片从种子 benchmark 抽取，没有联网取素材；目标是评测「出题模型」本身。
  • 对评测岗的意义：自动生成的评测集应该报告非核心率、区分度和家族偏差，而不只报模型得分。

08NodeSyn（Google Research）

09SearchArt（华为云）

  • 全称：SearchArt: Training Long-Horizon Search Agent with Scalable Synthetic and Verified Tasks
  • 机构 / 时间：Huawei Cloud Post-Training Team；arXiv 2026-07，v2 2026-08-11
  • 链接：arXiv 2607.24850；代码和数据未公开

三条造题流水线：DeepSearch QA（基于知识图谱）、DeepResearch QA（从综述反推问题）、真实用户体验 QA。和 K3 对照的重点是第一条。

一、图谱怎么建

1. 选种子（三个标准）

  • 模型见得少：从基于 Wikipedia 构建的大规模多语言知识图谱里抽长尾实体，优先选入度和出度都低的。目的是防止模型凭记忆直接答出来。
  • 结构够丰富：长尾实体常常在图里很稀疏，没法串出多跳链。所以对每个候选实体做多次随机游走，看局部邻域的拓扑；能稳定走到结构丰富子图的种子优先。
  • 领域均衡：种子挂在一棵层级领域 taxonomy 下，taxonomy 由预定义类别加上扩图过程中动态发现的新区域组成；各领域的采样配额实时调整。原文的理由是，图采样天然会集中在连接稠密的领域，忽略专门领域。

2. explorer agent 联网扩图

从种子实体或一个中间子图出发，agent 循环执行：生成查询 → 网页检索 → 知识抽取 → 建图 → 发现知识缺口。每轮的查询要超出图里已有的信息，不只查目标实体的直接属性，还要查相关实体、历史事件、组织关系、时间演变、地理关联和跨领域关系。

入图前做实体归一、消歧和规范化；重复或语义等价的关系合并，但保留每条事实的来源（由哪个查询发现、来自哪篇文档）。原文说合并后的全局图要满足三点：够深（支撑多步推理）、够广（支撑多样的搜索路径）、局部拓扑多样。

未公开：图的节点数和边数、扩图用的模型、扩图轮数。

二、怎么采样：难子图排序

从随机根实体出发批量采子图，可配置的参数包括最大实体数、扩展深度、分支宽度和每步的节点选择策略。每个子图从两个方面打难度分：

  • 结构复杂度：平均节点度（关系密度）、深度（从根到达全部实体所需的最小扩展深度）、宽度（并行证据分支数）。
  • 证据分散度 ESD：每条事实带着来源信息，按来源分组统计事实数，用变异系数 σ(n)/μ(n) 计算。原文的理由是：结构再复杂，如果证据集中在一两个网页里，搜起来也不难。

两项合成总分排序，只留最高分的子图出题。

三、怎么出题

  • 以子图为骨架：强模型基于子图生成多个候选，每个包含问题、答案和一条事实推理链。
  • 混淆：要求把实体名、关系描述、日期、地点和数值等表面常量模糊掉，让解题者只能从间接描述和关系约束里反推中间目标。
  • 之后还有「推理链迭代加长」和「以难轨迹为条件」两步继续加难度。

This Thuringian engineer married an Armenian woman whose father served as a general for a prominent royal figure. This royal figure sent the very first domestic telegram in his country to his brother. What specific city was this brother located in when he received this historic message? 答案：Shiraz

二、GraphSynth-15k：用约束随机游走造轨迹（四个阶段）

阶段 1：约束随机游走

  • 从 CWQ 训练集的 SPARQL 逻辑式里抽出谓词集合 P 和种子实体集合 E。用的都是训练集里见过的原子关系，但重新组合成没见过的拓扑结构，以此推动组合泛化。
  • 两类结构：
  • 2–5 跳的组合链；
  • 「交汇图」（2I）：从两个不同的主题实体出发，汇合到同一个目标实体。
  • 约束：每一步的关系必须在 P 里，而且从当前实体沿这条关系能到达的邻居数要落在 [d_min, d_max] 之间，既不能唯一（太简单），也不能分叉过多（没有信息量）。

阶段 2：出题和语义过滤

  • 用 Gemini-2.5-Pro 根据路径写问题，中间实体遮成 entity1、entity2，防止泄露答案。

阶段 3：模拟环境反馈

阶段 4：补思考过程

已知每一步的正确动作，用 GPT-4o-mini 写出「为什么选这一步」的推理，拼成完整轨迹。

12Graph2Eval（评测侧）

  • 全称：Graph2Eval: Automatic Multimodal Task Generation for Agents via Knowledge Graphs
  • 机构 / 时间：浙大、厦门大学、俄亥俄州立、蚂蚁集团；CVPR 2026，arXiv 2025-10，v3 2026-03-05
  • 链接：arXiv 2510.00507；GitHub 28⭐，最近更新 2026-01-10

一、流程

五步：数据接入 → 建 KG → 子图采样 → 生成任务 → 覆盖优化。同时产出两类任务：给 RAG agent 的文档理解题，和给 Web agent 的网页交互题。

二、图谱怎么建

数据接入

  • 文档：保留段落、表格、标题、图注等层级和版面结构，切成最小语义单元，做向量化，标上来源和位置元数据。
  • 网页：自动爬 URL，抓 DOM 和截图，并模拟人类操作去翻复杂页面；用规则加 LLM 评估剪掉低质量链接；另有安全约束，不采集敏感或受限信息。

节点：段落、标题、超链接、表单、按钮、表格单元格等，加上实体节点（人、地点、机构），并保留在 DOM 或文档里的路径。

边分三类：

  • 语义关系
  • 结构关系，例如指代、跨文档链接
  • 网页交互关系，例如页面跳转、表单提交、点击触发、版面或数据流

三、怎么采样和出题

  • 文档题：按任务目标的向量相似度（超过阈值）或结构匹配选节点，只保留相关类型的节点，然后从子图里抽出模板变量（节点内容、边关系、上下文、元数据），套任务模板，再由 LLM 生成。
  • 网页题（种子驱动）： 1. 先找页面上的可操作节点（按钮、输入框、表单、导航链接）作为种子； 2. 收集种子 k 跳内的邻居构成子图； 3. 用 meta-path 模式匹配和扩展成任务链； 4. LLM 结合子图、meta-path、页面截图和元素列表（Set-of-Marks）生成任务。
  • 原文例子：页面上只检测到搜索框、提交按钮和结果项，任务链就是「Search + Detail」；如果还有筛选器，就变成「Search + Filter + Detail」。

四、验证：覆盖优化

  • 用 LLM 或规则给候选题打质量分。
  • 在节点类型、边类型、模式、页面层级、网站类型、难度六个维度上量化覆盖。
  • 用多层相似度衡量新颖性，选出既高质量又有代表性的题。
  • 网页题用节点可达性分析保证可解。

五、规模与实验

  • Graph2Eval-Bench：共 1,319 题，其中文档理解 1,002 题，网页交互 317 题。
  • 消融：有 KG vs 无 KG
  • 设置：同一份数据，用 GPT-4o 各生成 1,000 题（文档、网页各 500）；两名标注员独立评一致性和可解性（两人一致才算），另用 Gemini 2.5 Flash 跑 agent 评测。
  • 结果：语义一致性平均提升 20%，可解性提升 17%。
  • 无 KG 版本的网页题大多局限在单页交互，多页工作流常常因为缺少页面之间的关系而做不了。
  • 有 KG 的题更能拉开不同尺寸模型的差距。

未公开：成本、各阶段淘汰率。

  • K3 的图是联网扩出来的全局概念图，Graph2Eval 的图是从给定的文档和网页里抽出来的局部结构图，用途是评测而不是训练。
  • 它的特点是把「可操作元素」也当成节点，任务链靠 meta-path 拼出来。这个思路可以直接用在个人助理类的 GUI 评测上。

13KNIGHT（评测侧）

  • 全称：KNIGHT: Knowledge Graph-Driven Multiple-Choice Question Generation with Adaptive Hardness Calibration
  • 机构 / 时间：德黑兰大学、Amirkabir 理工大学、TEIAS 等；arXiv 2026-02-23
  • 链接：arXiv 2602.20135；GitHub 1⭐，最近更新 2026-02-16

一、图谱怎么建：按深度上限做广度优先

输入是一个主题（加可选 prompt）和深度上限 d_max。算法 1 用先进先出队列，对每个节点循环做「检索 → 生成 → 过滤」：

  1. 检索：Contriever 稠密检索，在经过 BM25 预筛的 Wikipedia 语料上召回，再用 MiniLM-L12 交叉编码器把前 50 条重排到 5 条。
  2. 描述：GPT-4o-mini 根据这些段落生成节点的「八点说明」。如果检索分数都不超过 0.15，就退回到只用模型自身知识生成。
  3. 可追溯检查：节点说明和至少一段检索原文的重合度要 ≥ 0.35，否则丢弃这条说明。
  4. 抽三元组：从说明里抽三元组，用 Levenshtein 距离去掉近似重复。
  5. 审核：Wikidata 类型检查；用 NLI 检查节点说明和关系陈述是否一致；内容安全筛查。
  6. 新节点入队，直到深度达到 d_max。

KG 每个主题只建一次，缓存起来反复用。原文说之后出题就是「便宜地读一遍图」，不用每道题都重新读长文档。

二、出题

  • 在图上取多跳路径，路径越长、抽象程度越高，题越难。
  • 支持正向和反向两种出题方式。
  • 难度用熵类的不确定性指标和人类错误模式来校准。

三、验证（五条标准）

LLM 加规则的验证器检查：

  • 语法；
  • 唯一正确答案；
  • 选项不重复；
  • 能从证据里答出；
  • 切题。

「答不出」被当作生成器幻觉的代理指标。所有 LLM 调用都用 GPT-4o-mini。

四、结果

  • 做了历史、生物、数学三个领域，共 6 个选择题数据集。
  • 在 Google Colab T4 上几分钟就能生成。
  • 人工审计（每 100 题的违规数）：完整 KNIGHT 在重复、歧义、干扰项区分度、无法回答四项上都是最干净的。难度从 Level 1 升到 Level 3，违规数没有明显增加。
  • 生成题目给出的模型排名和 MMLU 类 benchmark 一致。

14SkillSynth（腾讯混元）

  • 全称：Toward Scalable Terminal Task Synthesis via Skill Graphs
  • 机构 / 时间：腾讯混元团队；arXiv 2026-04-28
  • 链接：arXiv 2604.25727；代码未公开

一、出发点

终端 agent 不是一次规划整个环境，而是在一连串中间状态里一步步决策。所以论文把轨迹抽象成「场景（决策点的状态）→ 技能（在这个场景下采取的策略）」的序列，并推导出训练目标可以按 p(场景)·p(技能|场景) 分解。结论是：要让模型学好，就要让训练数据在「场景 × 技能」上覆盖均匀，光堆题量不够。

二、技能图怎么建（四步）

  1. 筛技能：从 ClawHub 和公开 GitHub 仓库收集人写的技能，只保留满足四条的：能在 Linux 终端执行；有结构化工作流，不只是 prompt；不含对抗或越狱内容（例如从陌生 IP 下载文件、窃取环境变量里的密钥）；输出确定、可客观验证。
  2. 推场景：把每个技能的完整说明（Markdown 描述、代码、用例）交给 LLM，推出若干前置场景和后置场景，得到原子转移「技能：前置场景 → 后置场景」。
  3. 去重：对所有场景做向量化后聚类合并。试了 9 种聚类算法，最好的是「Louvain 粗分桶 + 层次凝聚聚类」。
  4. 跨技能对齐：每个后置场景用向量检索取最相似的 1,000 个前置场景，由 LLM 判断语义是否兼容；反方向再做一遍，用另一套 prompt。对齐后合并成统一的场景节点，最后由 LLM 再筛一遍所有（场景，技能，场景）三元组。原文说人工抽查表明每一步都必不可少；对齐标准和 prompt 在附录 B。

规模：82,073 个场景、57,214 个技能、185,529 条 LLM 验证过的连接。85.6% 的场景属于最大弱连通分量，另有 6,251 个小分量，对应专门的、自成一体的工作流。需要 7 个及以上技能的路径可以枚举出 16,632,220 条。覆盖音频语音、3D 仿真等长尾领域。

三、怎么采样：逆频率路径采样

  • 路径长度 1–7：1–3 是单技能任务，4 以上是组合任务。
  • 原文指出，均匀随机游走会集中在度数高的场景和常用技能上，所以给每个场景和技能计访问次数。起点按 1/(访问次数+1) 抽，每一步的出边按 1/(使用次数+1) 抽。
  • 同一路径内不重复访问场景和技能（单调推进）；技能组合和已有路径重复就丢弃。
  • 效果是让经验分布逐步趋近「场景 × 技能」上的均匀覆盖。

四、怎么出题

规划和实现分开。原文说，一次生成所有组件会让长输出质量不稳，而且模型会陷进实现细节、题目不够复杂。所以先由 planner 把路径转成子目标和预期输出的结构化计划，再由带工具的 constructor 按计划生成完整任务：指令、环境、oracle 解法、验证脚本。原文图 4 给了一个视频领域的例子，任务最后要求保存 GIF 和输出元数据。

五、验证与修复

  • 执行验证：在容器里用验证脚本跑 oracle 解法，确认可解。
  • rubric 验证（LLM 评审）：一是指令和测试是否对齐，既不能太松（漏掉要求的功能），也不能太严（加了指令没说的约束）；二是指令是否自洽，不能泄露解题进度的提示。
  • 任一项不过就把诊断反馈给 constructor 修，最多 3 轮，每轮最多 20 次工具调用。

产出数字：

  • 3,721 条路径得到 3,560 个可用任务；95.7% 通过 oracle 检查，92.0% 两项都通过。
  • 修复循环救回了 721 个第一轮失败的任务。
  • rubric 失败里 77% 是测试过严或过松。这些任务仍保留给 SFT，但不给 RL 用，免得奖励信号出错。
  • oracle 失败的主因是文件系统快照损坏，第一轮生成坏了往往修不回来；用更高温度重跑是简单有效的补救。
  • 平均每个合格任务 $27.3。

难度分布：用 Hy3 Preview 每题做 3 次，37% 落在 1/3 或 2/3 的「可学区间」，38% 三次全失败。Claude Opus 4.6 平均要 37 步才能解，三次独立 rollout 后仍有 121 道没解出来。

六、实验与消融

  • 训练设置：教师模型 MiniMax M2.7（因为便宜），每题采 3 条，共 10,680 条轨迹；成功和失败的轨迹都保留。对 Qwen3-8B、14B、32B 全参 SFT，学习率 2e-5，训 5 轮；评测用 Terminal-Bench 1.0（80 题）和 2.0（89 题），框架是 Terminus 2。
  • 主结果：三个尺寸都超过各自基线，模型越大收益越大；Qwen3-32B + SkillSynth 在 TB 2.0 上超过更大的 Qwen3 Coder 480B。
  • 种子消融：同一套多 agent 流程，对比 3,721 个随机单技能种子、3,721 个随机 2–7 技能组合。SkillSynth 比单技能高 8.4 分（TB 1.0）和 8.3 分（TB 2.0），比随机组合高 3.0 和 3.8 分。原文的解释是，随机组合的技能之间没有先后依赖，出来的题「要求多但步骤少」。
  • 多样性：SkillSynth 的轨迹在「场景–技能」对上的独特覆盖比单技能多 31%，比随机组合多 19%。

七、与 K3 4.2.2 对照

  • 相同：都是自动建图、去重合并节点、按图采样后再交给 agent 出题。
  • 不同：
  • K3 的节点是知识概念，目标是知识覆盖；SkillSynth 的节点是「状态」，边是「技能」，目标是解题轨迹的覆盖。
  • 原文明确批评，用 LLM 生成的 taxonomy 扩领域覆盖常常偏离真实使用，所以它的节点全部来自真实的人写技能。
  • K3 没写采样算法；SkillSynth 给出了逆频率采样的伪代码，正好可以解决「热门节点被反复采到」的问题。

15ToolVerse（美团 LongCat）

  • 全称：ToolVerse: Unlocking Massive Environments and Long-Horizon Tasks for Agentic Reinforcement Learning
  • 机构 / 时间：美团 LongCat Interaction Team、北大、复旦、武大；arXiv 2026-07-17
  • 链接：arXiv 2607.15660；代码未公开
  • 和你看过的 VitaBench 同属美团 LongCat。

一、环境怎么建

起点是一批原始工具集（每个对应一个功能领域）。

  1. Schema 重构：对齐函数签名和实际功能，去掉文本噪声。
  2. 领域字典数据库：为每个工具集建一个小数据库，存库存、用户资料这类状态变量，工具调用才有状态。
  3. 生成可执行函数：用 MCP 工具库写出读写数据库的 Python 函数。
  4. 单元测试：自动生成单元测试，只保留语法检查和单测全部通过的工具集。约 20% 的初始工具集在这一步被过滤掉。

最终规模：422 个环境、4,438 个可执行工具，平均每个环境 12.2 个工具，覆盖 8 个大领域。

二、工具依赖图

每个场景一张图，节点是工具。边由 LLM 按两条原则推断：

  • A 的输出是 B 的输入，就连 A→B；
  • 场景逻辑里 B 只能在 A 之后调用，也连 A→B。

用之前先去掉环和不可执行的依赖。每个工具集生成 3 张不同的依赖图，覆盖不同的逻辑流。

三、怎么采样：动态解锁采样（DUS）

  • 维护一个「就绪队列」，里面是入度为 0 的工具，起点通常是基础操作。
  • 每一步从队列里抽一批（k = min(|队列|, N)）组成一个阶段；执行后把后继节点的入度减 1，减到 0 就进入队列。
  • 依赖多的工具在前置完成之前一直「锁着」，避免因果错误。
  • 原文说这样会自然形成由易到难的课程：简单查询一定在复杂操作之前。
  • 每张图采 5 个任务。

四、怎么出题：逆向重建上下文

  1. 采样得到的工具骨架先放到 mock 数据库里落地，按拓扑序填参数：有依赖的参数取前一个工具的输出，与上下文相关的参数从数据库当前状态里取，得到一条可执行的 Golden Trace。
  2. LLM 把 Golden Trace 改写成面向用户的任务，生成时把相关的依赖边也给它，保证参数和语义依赖不丢。
  3. 每个环境采多条 trace，尽量让所有工具都被用到。

五、验证与过滤

  • 用 LangGraph 重放，确认 Golden Trace 在有状态的数据库更新下仍然可执行。
  • Pass@8：教师 agent 最多做 8 次，至少一次轨迹得分为 1 才保留，否则丢弃。原文举例的教师模型有 GPT-4.1、DeepSeek-V3.2，实际选的是和策略模型分布接近的 Qwen3-32B。
  • 每个环境最多保留 10 个任务，防止过拟合到特定场景。

最终规模（GUST 数据集）：2,987 条数据，每条 3–7 个子任务，平均 3.8 个。各阶段的淘汰率见原文图 4，正文没有给出具体百分比。

六、训练与实验

  • 训练：对 Qwen2.5-14B-Instruct、Qwen3-4B、Qwen3-8B 做 RL（GRPO 和他们提出的 TARA），用 DeepSeek-V3.2 当用户模拟器。奖励按每轮工具调用和 Golden Trace 的覆盖率计算。
  • 主结果（Qwen3-8B Thinking，基线 → +ToolVerse w/ TARA）：
  • τ²-Bench Overall 28.88 → 37.50（+8.62）
  • BFCL Multi-Turn Overall 27.87 → 32.37（+4.50）
  • ACEBench-Agent 46.51 → 61.66（+15.15）
  • 环境数量消融（Qwen3-8B）：100 / 200 / 300 / 422 个环境。原文正文说，从 100 增加到 422，BFCLv3 从 35.00% 升到 37.50%，τ²-Bench 从 27.33% 升到 32.37%；结论是环境多样性比在固定环境里多做 rollout 更重要。注意：表 7 的列标签和正文说法对不上（列名顺序是反的），引用时以正文为准。

七、局限（原文）

  • 依赖关系来自已有协议里预定义的依赖，和能自主发现新工具交互的环境相比，涌现行为的多样性可能受限。
  • TARA 仍依赖每一轮都有定义好的奖励，在奖励很稀疏或含糊的场景下可能不够用。

八、与 K3 4.2.2 对照

  • 相同：都是「先有结构，再按结构采样，再让 LLM 写成题」。K3 的个人助理环境里有模拟的 Gmail、Notion、Slack，和 ToolVerse 的 mock 数据库思路一致。
  • 不同：ToolVerse 的图描述的是「工具之间的先后依赖」，不涉及知识覆盖；题目是从可执行轨迹倒推出来的，所以答案天然可验证，而 K3 4.2.2 是先有素材再出题。

16GAIS

  • 全称：Scaling Agentic Capabilities via Grounded Interaction Synthesis（Grounded Agentic Interaction Synthesis）
  • 机构 / 时间：中国人民大学、北大、腾讯；arXiv 2026-06-01
  • 链接：arXiv 2606.02001；GitHub 0⭐，最近更新 2026-06-08

一、出发点

原文认为，完全靠 LLM 生成环境和任务，往往会退化成对模型内部先验的有偏随机采样，抓不住真实领域的多样性和难度。所以环境要「锚定」在真实协议上。

二、环境：锚定真实 MCP 仓库

  • 收集 1,174 个仓库、14,395 个工具，最后留下 707 个仓库、9,488 个工具。其中 4,157 个工具为了能执行做了简化，用严格的单元测试保证环境完整。
  • 工具分两类：读工具（数据库查询、查天气等）和写工具（会修改状态）。
  • 功能难度过滤：按附录的标准给每个工具打 1–5 分。只有简单工具（≤2 分）或工具少于 3 个的环境丢弃。
  • 原文图 3 对比了几种环境构建方式的工具分布：真实协议锚定的环境不只有常见工具，分布更均衡。

三、工具依赖图和出题

  • 每个环境建一张工具依赖图，边表示 A 的输出是 B 的输入；成对的因果关系由 LLM 判断。
  • 锚点：从复杂或处于中心的工具出发规划有向游走，作为任务骨架（Golden Tool Chain）。游走围绕写工具展开，因为写操作需要更复杂的工具间依赖。
  • 对抗策略：给任务注入领域政策，要求 agent 处理约束。

原文图 3 示例：

  • 用户意图：「会议改期，需要取消去纽约的航班」
  • 黄金工具链：list_reservations → get_flight → cancel_reservation
  • 环境初始状态：当前时间 2026-01-20 08:00，航班 14:00 起飞
  • 政策：「起飞前 24 小时内严禁取消或修改」
  • 对抗变体：模拟用户声称「我有急诊」并要求破例；agent 应当回答「根据取消政策，您的航班无法取消」

四、交互模拟与过滤

  • 模拟用户有人设和「信息披露意愿」两个属性。
  • 过滤同时看状态（最终环境状态对不对）和回复（是否守住政策）。

五、实验与消融

  • 在 BFCL-V3、τ²-Bench、ACEBench 上，基座模型用 GAIS 数据训练后超过其他数据集训练的结果，能追平甚至超过官方指令模型。原文还说它用更少的数据达到了更好的效果。
  • 消融（Qwen3-8B-Base，BFCL-V3）：
  • 环境多样性：含写操作的子集明显好于只读子集，完整数据集最好；
  • 环境难度：高难度子集（4–5 分）好于低难度（1–3 分），但完整分布最好；
  • 任务依赖复杂度和政策约束也做了消融，都有贡献。
  • 各项具体数值在原文图 5 里，正文没有逐项写出。

未公开：成本。

六、与 K3 4.2.2 对照

  • K3 的个人助理环境（模拟的 Gmail、Notion、Slack）和 GAIS 的思路一致：环境要真实，任务要带政策约束。
  • GAIS 的结构是工具依赖图，不是知识图谱。
  • 「难度过滤 + 完整难度分布最好」这个结论和 LongCrafter 一致：只挑难题不如按结构把难度铺开。

17FireFly

  • 全称：Firefly: Illuminating Large-Scale Verified Tool-Call Data Generation from Real APIs
  • 机构 / 时间：东北大学（Northeastern University）及多位独立研究者；arXiv 2026-05-17
  • 链接：arXiv 2605.17558；代码和数据在匿名链接（anonymous.4open.science）

一、核心思路：先探索，后出题

原文说，常见做法是「先生成任务，再希望它能解」。FireFly 反过来：先让强模型在真实 API 上探索，再根据观察到的结果倒推出任务。因为每个状态都是真实执行得到的，可达性和标准答案的正确性在构造时就有保证。

二、工具图

  • 工具来自 smithery.ai 上的真实 MCP 服务器，共 240 个服务器、993 个工具。
  • 节点是工具，边表示「A 的输出可以转换成 B 的输入」。原文指出只做 schema 类型匹配太粗（两个 string 字段可能毫无关系），所以由 LLM 根据工具描述和 schema 判断每一对，给出高 / 中 / 低置信度。
  • 规模：约 8.3 万条有向边，平均每个工具 88 个后继，其中 6.4 万条是中等以上置信度；有服务器内的边，也有跨服务器的边。

三、DAG 探索

  • 起点选至少有两个高置信度后继的工具，这样可以分叉。
  • 每一轮给强模型一组随机后继，范围是所有已完成节点的后继的并集，且只取中等以上置信度。模型可以并行调用多个工具（扇出）、串一个后继（顺序）、或把前面多个节点的输出合并成一次调用（扇入）。
  • 到达调用预算或没有后继为止，得到一个 DAG，每个节点记录工具、输入和输出。

四、倒推出题

  • 从 DAG 里选一部分节点，围绕它们写自然语言任务：任务里写清填参数需要的信息（名称、参数、约束），答案从所选节点的输出里取；没选中的节点作为干扰或无关的探索路径。
  • 每个任务带结构化的答案 schema（带命名占位符的 JSON 模板）和答案句模板，可以逐字段比对，而不是自由文本匹配。
  • 同一个 DAG 换不同的节点子集、换说法，就能得到多个复杂度不同的任务。

五、验证

LLM 评审按五条标准检查每个「任务 + 轨迹」：

  1. 可验证：答案能客观检查；
  2. 明确：只有一个正确答案；
  3. 可理解：输出是人能看懂的，不是不透明的 ID；
  4. 真实：0–10 分里至少 5 分；
  5. 难度校准：声称的难度和轨迹复杂度相符。

任一条不过就删，这一步约淘汰一半。

六、离线模拟器

真实 API 的数据会变（天气、股价、搜索索引），服务器也可能宕机或限流。所以把探索时记录的每次调用建成索引，训练和评测时按三层查找：

  1. 参数哈希精确匹配，返回缓存结果；
  2. 检索相近的调用，重建回复；
  3. 都没有就返回错误。

原文说这是有意保守：标准答案来自已知轨迹，偏离太远的调用本来就不该成功。

七、成本与规模

  • 数据：5,144 个验证任务，9,749 条轨迹，240 个服务器，993 个工具。
  • 成本：全部用 Claude 4.5 Sonnet（AWS Bedrock 批量推理）生成，约 235 亿 token（输入 214 亿，输出 20 亿），总花费约 $47K，摊到每个任务约 $9。原文说这是一次性投入，之后离线 RL 不再产生 API 费用。这个 $9 是按 $47K ÷ 5,144 算的，原文没有直接给出单题成本。

八、实验

  • 自建测试集：Qwen3-4B 用 GRPO 训练后，pass@1 从 28.1% 到 41.5%（+13.4），Claude Sonnet 4.6 是 42.2%；pass@8 达 52.8%，超过 Sonnet（50.3%），接近 Opus（54.4%）；pass@16 是 57.0%。
  • 公开 benchmark：Tau2-Bench（Retail / Airline / Telecom）、MCPMark、MCP-Atlas 都有提升。

九、与 K3 4.2.2 对照

  • K3 是「素材 → 出题」，FireFly 是「执行 → 倒推出题」。后者用在工具类任务上，天然解决了标准答案对不对的问题。
  • K3 的 RL 环境里，自主执行类任务有隐藏校验和有限提交次数；FireFly 的离线模拟器则是另一种保证可复现的思路。

18EnvFactory

  • 全称：EnvFactory: Scaling Tool-Use Agents via Executable Environments Synthesis and Robust RL
  • 机构 / 时间：港科大（广州）LARK、华为、剑桥、UCL、港科大；arXiv 2026-05-18
  • 链接：arXiv 2605.18703；GitHub 96⭐，最近更新 2026-08-28

一、环境怎么建（EnvGen，三个 agent）

  1. 提案：Search Agent 先分析现有环境池有哪些覆盖缺口，再去检索真实来源（API 文档、技术报告、用例），写出新环境的元数据，包括描述、工具定义和 schema。这一步和 K3 的「agent 联网补覆盖」很像，只是补的是环境而不是知识。
  2. 数据库建模：Code Agent 根据元数据推出有状态的数据库结构，用 Pydantic 定义，保证每次 rollout 相互隔离、可复现。
  3. 写代码：为每个工具实现 Python 代码，包装成 MCP 接口。
  4. 修订循环：Test Agent 写单元测试，按四条标准检查：接口和元数据一致、能导入能执行、结果符合预期、调用后数据库状态正确转移。失败就出结构化错误报告（定位到实现逻辑等）给 Code Agent 修，直到通过或达到修订上限。

规模：7 个领域、85 个验证环境、842 个工具。原文强调，它用的环境数只有前人的约五分之一。

二、工具依赖图

  • 先用语义匹配建图，把工具和参数都当成节点，以抓住非线性的依赖。
  • 再用 LLM 修正。原文的理由是：语义匹配快但会漏掉隐含的逻辑关系，纯 LLM 推断灵活但贵，而且结果可能不一致。
  • 没有参数的工具也要靠语义匹配连进图里，否则会成为孤立节点。

三、怎么采样：拓扑感知采样

约束：采到的工具，每个必填参数要么由用户提供，要么来自前面采到的工具的输出。

  • 分内外参数：LLM 把每个参数标成外部参数（城市、姓名这类用户知道的）或内部参数（例如 book_hotel 需要的 hotel_id，来自 get_hotel_list 的输出，用户不可能记得）。
  • 补依赖：一个参数如果是可选的、外部可提供的、或者内部参数但前面已经有工具产出，就算已满足；否则沿反向边递归找一个能产出它的前置工具。另外以小概率 p 随机加入前置工具，增加多样性。
  • 扩邻居：依赖补齐后，沿出边随机选 1 到 k 个邻居扩展，形成分叉的非线性链。
  • 原文指出，普通随机游走只能表达顺序逻辑，也常常补不齐「一个工具需要多个上游输出」的情况。

四、出题（QueryGen）

两个原则：

  1. 真实的用户意图：反复生成和修改自然的意图，加入隐含推理和歧义，把「指令清单」改成真人会说的话；
  2. 可验证的标准答案：在沙盒里实际交互，生成验证过的工具调用轨迹。

流程是：基于工具链先构造用户画像和场景，再推出数据库初始状态，然后生成查询，跑轨迹，最后过滤并选出一条通过的轨迹。prompt 在附录 I。

19ASTRA（贝壳）

  • 全称：ASTRA: Automated Synthesis of agentic Trajectories and Reinforcement Arenas
  • 机构 / 时间：贝壳 Beike Language and Intelligence；arXiv 2026-01，v2 2026-01-30
  • 链接：arXiv 2601.21558；GitHub 156⭐，最近更新 2026-01-30。流水线、环境和模型全部开源。

两条线：SFT 用工具调用图造轨迹；RL 把多跳问答拆成可执行、可规则验证的环境。

一、SFT：工具链图

收集和过滤 MCP 服务器，三条标准：

  • 工具少于 3 个的丢弃；
  • 描述含糊到无法判断功能的丢弃；
  • schema 无法转成 OpenAI 风格调用格式的丢弃。

最终保留 1,585 个 MCP 服务器、19,036 个工具文档，覆盖 41 个领域。

建图（只在同一个服务器内部组合工具）：

  1. 对每个服务器，LLM 同时写出一个可能的任务和解决它的工具链；
  2. 把这些链里所有「相邻出现」的工具对汇总成一张有向转移图，边带权重；
  3. 在图上做长度受限、按权重偏置的随机游走，作为候选链。

这里的图不是从 schema 推出来的，而是从 LLM 多次「设想的用法」里统计出来的。

依赖验证：检查每个工具的必填参数是否都能由任务描述或前面工具的输出提供；任务和链不匹配的丢弃。

出题：

  • 两种来源：按验证过的链生成（偏向可执行），和只给服务器说明生成（偏向话题和语言覆盖）。
  • 再沿三个方向扩写：多样性（换说法、换偏好或背景）、复杂度（加约束、隐含指代、追问），以及保持意图一致。
  • 最后打分过滤。

执行：已部署的服务器真实调用；只有文档的服务器用有状态的工具回复模拟模块。

二、RL：把问答分解成可验证环境

  • 给定领域知识源 K 和跳数预算 H，要么把一个主问题拆成子问题，要么直接生成一个需要大约 H 跳的问题。同时产出主问题、答案和中间子问答，答案按子问题的依赖结构（链或 DAG）汇总。
  • 过滤：
  • 中间子问题不需要调用工具的样本（纯语言操作，如评价、摘要、推荐、排序、格式转换）剔除。只允许叶子节点是不调工具的汇总步骤，因为非叶节点不调工具会打断工具链，无法构成完全可验证的环境。
  • 剩下的从四个方面打分，例如依赖一致性：LLM 逐个检查每个子问题列出的依赖是否都必要，按子问题取平均；另一项是子问题的原子性。
  • 再把每个子问题变成可执行、可规则验证的环境，做多轮 RL；奖励按子任务完成度计算，同时兼顾交互效率。

三、实验

  • 模型：Qwen3-14B 和 Qwen3-32B，SFT 训 2 轮，学习率分别是 5e-6 和 2e-6。
  • 结果：BFCL-MT、τ²-Bench、ACEBench 上，同参数量下达到最好，能和更大的开源及闭源模型竞争；SFT 和 RL 都有提升，RL 贡献最大。例如 BFCL-MT Base 子项，Qwen3-14B 从 54.00 到 SFT 后 67.50。
  • AIME 2024/2025：几乎没有退化。
  • 消融：无关工具混入：RL 时只给正确工具效果最差，策略会过拟合到很窄的选工具模式；随机混入 5–9 个其他领域的工具更好。

未公开：成本、每阶段淘汰率。

四、与 K3 4.2.2 对照

  • K3 的 RL 部分也有「工具环境可以切换成模仿不同 harness」的设计，和 ASTRA「混入无关工具防止过拟合」是同一类思路：防止模型只适应一种环境。
  • 图谱层面，ASTRA 的工具图是从 LLM 设想的用法里统计出来的。这和 SkillSynth 批评的「LLM 生成结构偏离真实使用」正好相反，可以在面试里对比讲。

D 自动建树

20ATLAS

  • 全称：ATLAS: Agentic Taxonomy of LArge-Scale Software Ecosystems
  • 机构 / 时间：中科院软件所、国科大、南洋理工、南开等；ASE 2026（2026-10-12 至 16，慕尼黑），arXiv 2026-06
  • 链接：arXiv 2606.21597；ACM DL

这篇只建分类树，不造题。但它把「agent 怎么长出一棵好树」写得最细，而且明确借用了生物分类学。和植物识别数据全集的思路最接近，也最能补 K3 没写的部分。

一、问题

GitHub Topics 是扁平的、不一致的，只覆盖 67% 的仓库。纯靠 LLM 知识设计分类会脱离真实分布；纯靠聚类又得不到可解释的分类维度；而且几万个仓库塞不进一个上下文。

二、怎么建：广度优先、自上而下，每个节点跑一个「设计 → 分类 → 修正」循环

1. 设计维度（Designer Agent，Claude Opus 4.6）

  • 输入是这个节点下随机抽的 80 个仓库（约 2.2 万 token），加上「路径上下文」：从根到当前节点所有祖先的名称、定义和切分维度。
  • 路径上下文有两个作用：一是防止重复用维度，比如深度 1 已经用过「功能领域」，深度 3 就不会再用；二是强制由粗到细，要求选比祖先更具体的维度。
  • 维度稳定性原则（原文明确借鉴生物分类，界、门这类高阶分类比属、种稳定得多）：上层维度要选稳定的本质特征，比如功能领域、制品类型；下层才用易变的特征，比如目标平台、实现方式。这样生态演化时只会扩展叶子，上层骨架不动。
  • 输出：维度描述，若干子类（每个有名称、定义、纳入标准），以及选择理由。

2. 批量分类（Classifier Agent，Claude Sonnet 4.6）

每个仓库给出类别（或「无合适类别」）、置信度和简短理由。「无类别」表示覆盖缺口，「低置信度」表示类别边界有歧义，两者分别指向不同的修法。

3. 修正循环（按代价从低到高逐级升级）

用「无类别率」r⊥ 作信号，r⊥ > 0 就触发修正：

  1. 加类别：只重分失败的仓库，最便宜；
  2. 改定义：失败和被挤出来的仓库重新分类；
  3. 换维度：全部从头重分，最贵。

规则：

  • 一个策略用完 r⊥ 没下降，就升级到下一级；
  • 降级规则：r⊥ < 0.5 时即使该换维度也退回到「加类别」，局部失败不推翻整个维度；
  • Designer 会看到修改历史，避免重复失败的做法；
  • 大节点在分类过程中，一旦实时的无类别率超过动态阈值就提前中断，省掉几千次无效调用。

4. 单层校验：检查是否 MECE（相互独立、完全穷尽），必要时合并、拆分、重命名，然后子节点入队。

5. 层级对齐（后处理）

  • 不同分支的深度不能直接比，要比的是「切分维度序列」。
  • 用 LLM 分析分层抽样的根到叶路径，归纳出语义等级（例如「制品性质 → 领域类别 → 功能专长 → 技术关注点」），每个维度按多数投票分到一个等级。
  • 检查有没有从粗等级直接跳到细等级的分支；有就插入中间节点补上。单子节点的冗余中间层合并。

原文图 1 的一条路径：Software → Library/SDK（15,509）→ UI & Gfx（4,764，维度「UI Functional Role」，分 19 类）→ Web（356）→ React（135）……；另有 Standalone App（8,814）、Media & Creation（992）、Video Playback（59）等节点。

规模：对齐后 36,986 个节点，54,387 个仓库，8 个语义等级（R0–R7）。有的分支深到第 8 级，有的到第 4 级就停，原文说不同领域需要的细致程度不同。

三、评测

  • 数据：截至 2026-02-20，GitHub 上 ≥1,000 星的 55,083 个仓库，最后用 54,387 个。
  • 质量：在 2,001 个仓库的分层样本上 TQF 83.13%，比最强基线高 15 个点；全量约 73.0%（原文说差距主要来自路径粒度指标对长路径「全对才算对」）。
  • 下游任务：找替代软件 P@1 = 85.71%，人工整理的列表只有 62.34%。
  • 评审：用 GPT-5.4 交叉验证 LLM 评审结果，42 组「方法 × 指标」的 Pearson r = 0.995。

212024–2025 前作精读

下面 7 篇早于本页的一年窗口，是近一年方法的直接前身，所以写得短一些。

GLAN（Microsoft，2024-02）

  • 做法：完全不用种子样本，只用一棵预先整理好的「人类知识与能力」分类树。仿照教育体系，用 LLM 半自动地把知识拆成领域 → 子领域 → 学科（学科数量有限，人工核验成本低），再为每个学科列出科目，为每个科目写教学大纲，用大纲里每节课的关键概念生成指令。
  • 结果：在 Mistral 上，数学推理、代码、学术考试、逻辑推理和通用指令遵循都有提升，并且没有用这些任务的专门训练数据。
  • 扩展：新增领域只需在树上加一个节点。
  • 与 K3：同样是自顶向下拆知识，但 GLAN 的树主要靠模型记忆，没有联网取材。

Condor（上海 AI Lab，2025-01）

  • 做法：让 LLM 生成世界知识标签，再自回归地补全由粗到细的标签链，以标签为种子生成问题和初始回答，然后自我反思、改写回答。
  • 结果：只用 2 万条 Condor 数据，就超过了 LLaMA3.1-8B 官方版本（原文图 1）。
  • 与 K3：同为标签树驱动，面向通用对话 SFT，没有可验证的答案。

SHARP（2025-05）

  • 做法：面向 STEM 方向的 RLVR 出题。三阶段框架为对齐（Alignment）、实例化（Instantiation）、推理（Inference），用「三级类目」知识体系保证主题多样，目标难度为研究生和奥赛级，要求逻辑一致、答案无歧义可验证。由最强推理模型出题并自验证，再用于强化学习。
  • 结果：在 GPQA 等基准上明显优于已有合成方法。
  • 与 K3：分类树 + 可验证答案，和 K3 的出题思路最接近，但没有真实素材检索。

TaskCraft（OPPO，2025-06）

  • 做法：先生成只需一个工具就能解决的原子任务，再做深度扩展（串联成多跳）和宽度扩展（并列合并），得到难度可调、多工具、可验证、附带执行轨迹的 agent 任务。
  • 规模：约 3.6 万条任务，代码和数据开源。
  • 与 K3：不靠树，靠原子任务组合；可以看作 K3「多节点组合」的另一种实现。

WebSailor（阿里通义，2025-07）

  • 做法：用结构化采样构造高不确定性的实体图，再做信息模糊化（隐藏关键信息），得到 BrowseComp 风格的难题；冷启动只用了 2 千多条高质量 RFT 数据，再用 DUPO 算法做 agent RL。
  • 结果：在 BrowseComp-en/zh 上超过所有开源 agent，并超过 Grok-3 等闭源产品。
  • 与 K3：图上随机游走 + 模糊化，属于「图采样出题」一派。

WebShaper（阿里通义，2025-07）

  • 做法：先形式化、后取材。用集合论的知识投影（Knowledge Projection, KP）组合来定义推理结构，先造种子题（共 1.8 万道，保留至少有一次 rollout 答对的），再由一个带检索和验证工具的 Expander agent 逐步把形式化问题扩展得更复杂。
  • 结果：在 GAIA 和 WebWalkerQA 上取得开源信息检索 agent 的最佳成绩。
  • 与 K3：先定结构再找材料，和 K3「先树后取材」思路相同。

DeepDive（清华 / 智谱，2025-09）

  • 做法：在开放知识图谱上随机游走、组合多个模糊实体，自动合成难以检索的问题；再用端到端多轮 RL 训练，并加入冗余惩罚，抑制重复相似的查询。
  • 结果：DeepDive-32B 在 BrowseComp 上超过 WebSailor、DeepSeek-R1-Browse 和 Search-o1，并且工具调用次数和并行采样都能带来测试时扩展。全部开源。
  • 与 K3：直接取材于知识图谱。K3 的素材是网页、论文和代码，覆盖面更广，但没有图结构可以保证答案唯一。

类比

23和植物识别数据全集

植物识别的做法：先用物种分类（界门纲目科属种）定义「全集」，再在每个叶子上找图片，按类目补齐数量，长尾物种单独补采。对照下来：

植物识别 K3 / 本页的工作
物种分类树（现成，生物学定好） 概念图谱（K3、SearchArt 由 agent 长出来）或能力 taxonomy（CLI-Universe 人定）
叶子是「种」 叶子是「足够原子的概念」（K3）、技能（SkillSynth）、实体（SearchArt）
按物种搜图，搜索词带上科属避免同名 关键词拼祖先上下文检索（K3）；只带祖先链做决策（ATLAS）
每类保证最少样本数，长尾单独补 按领域配额采样并动态调整（SearchArt、BenchBench）；专挑模型见得少的长尾实体（SearchArt）
图片人工审核、去重 可执行校验、fail-to-pass、多模型评审组（CLI-Universe、SkillSynth、BenchBench）
分类本身有争议时要修树 分类失败反过来修维度（ATLAS）

两点不同：

  1. 物种树是现成的、公认的；LLM 训练的知识树没有标准答案，所以 K3、SearchArt、ATLAS 都让 agent 边查边长树，树本身也成了产出。
  2. 植物数据是「一个叶子对应一堆样本」；造题经常要「多个节点组合」（K3 的 RoPE + GPU kernel、STEPS 的技能组合、工具图上的路径），组合怎么挑是新的问题。

面试

24可以讲的观点

  1. 覆盖率要靠结构管，不能靠模型自由发挥。 让模型自由出题会集中在它熟悉的热门知识上。SearchArt 原文直说图采样会偏向稠密区域，所以要用 taxonomy 和动态配额拉平；SkillSynth 则批评 LLM 生成的 taxonomy 偏离真实使用，改从真实技能建图。面试可以讲：覆盖地图从哪来（人定、模型推、agent 联网长、真实日志），各有什么偏差。
  2. 「采样 → 真实素材 → 出题」的关键在中间一步。 K3 和 CLI-Universe 都要求先拿到真实网页、仓库、issue，再出题。这一步决定题目是否有据可查、是否有真实的坑，也是数据公司能和模型公司自产数据拉开差距的地方。
  3. 验证成本才是大头。 CLI-Universe 淘汰约三分之二候选；SkillSynth 每个合格任务约 $27.3、通过率 95.7%；FireFly 用「先观察结果再倒推题目」让答案构造即正确。谈数据生产线时，应该先讲淘汰率和单题成本，再讲产量。
  4. 图的节点类型决定能练什么能力。 概念节点练知识覆盖（K3），实体节点练多跳搜索（SearchArt、DeepDive），工具或技能节点练执行轨迹（SkillSynth、ToolVerse）。设计评测时先问清楚：要测的是知识面、搜索深度，还是工作流执行。
  5. 评测集本身也可以这样生成和体检。 BenchBench 发现出题能力和答题能力只中等相关（ρ≈0.37），无效题会拉低区分度（r≈−0.62）；Graph2Eval 用可达性分析保证可解。做评测岗可以讲：自动生成的评测集要报告无效率和区分度，而不只是模型分数。
