Agent 轨迹数据：怎么造、怎么评、谁在卖

2026-10-14 · 另见：Agent 评测论文精读 · 知识图谱造题 · Tech report 数据部分 轨迹是 agent 完成一个任务的完整过程：每一步看到了什么、想了什么、调了什么工具、环境返回了什么，最后成没成。它既是 SFT 和过程监督的训练数据，也是过程评测的对象。本页按构建方式整理近一年的代表工作，数字和措辞来自论文摘要或原文，原文没给的标「未公开」。

构建方式

01rollout + 过滤

做法：先有可执行的环境和能自动判对错的任务，再让强模型（或正在训练的模型）多次采样，只保留判为成功的轨迹，也就是拒绝采样。判官可以是单元测试、规则、LLM judge 或训练出来的 verifier。

代表工作

  • SWE-Gym（2024-12）：2,438 个真实 Python 任务，每个带可执行环境和单元测试。用采样出的轨迹微调 agent，SWE-Bench Verified 和 Lite 上 resolve rate 最多提升 19 个百分点；又用轨迹训练 verifier 做推理时筛选，Verified 32.0%、Lite 26.0%。轨迹已公开。
  • SWE-smith（2025-04）：思路是「先造任务再跑轨迹」。给任意 Python 仓库建执行环境，自动制造让已有测试失败的 bug，得到 128 个仓库、5 万个任务。SWE-agent-LM-32B 在 SWE-bench Verified 上 40.2% Pass@1。轨迹公开。
  • SWE-rebench（2025-05）：从 GitHub 持续抽取真实任务，2.1 万+ 个，既用于 RL，也拿新任务做防污染评测。
  • Kimi K2（2025-07）：3,000+ 真实 MCP 工具，演化出 20,000+ 合成工具；任务配 rubric；多轮轨迹由 LLM 模拟用户生成，再由 LLM judge 按 rubric 过滤。
  • WebSailor（2025-07，通义）：先用结构化采样和信息混淆造高不确定性的搜索题，再做 RFT 冷启动（拒绝采样微调），然后 RL。

质量控制：判官准不准决定一切。单元测试最可靠，但只适用于代码；开放任务要靠 rubric + LLM judge。

坑：只留成功轨迹，模型学不到出错后怎么办；强模型的风格和偏好会被整体继承；判官有漏洞时，「投机成功」的轨迹也会被留下。

构建方式

02人工示范

做法：标注员在真实电脑、手机或浏览器上完成任务，录制工具记下截图、动作和时间。之后通常还要补上每一步的「思考」，因为人做任务时不会把想法写下来。

代表工作

  • OpenCUA（2025-08）：开源了录制标注工具；数据集 AgentNet 覆盖 3 个操作系统、200+ 应用和网站，是第一个这个规模的电脑操作任务集；再把示范转成状态-动作对，并补上带反思的长思维链。OpenCUA-72B 在 OSWorld-Verified 上平均成功率 45.0%。
  • ScaleCUA（2025-09，上海 AI Lab）：覆盖 6 个操作系统、3 类任务，用「自动 agent + 人类专家」闭环生产数据。
  • Aguvis（2024-12）：汇总了多源 GUI 数据，补充 grounding 和推理标注，分两阶段训练。

成本：训练用人工示范的单条成本，以上论文的摘要都没有给出，标为未公开。评测侧可以参考 Mind2Web 2：130 道长程搜索题，构建花了 1000+ 小时人工。

坑：人的操作路径和模型不同，比如人会凭记忆跳步；补出来的思考是事后写的，未必反映真实决策；录制涉及隐私，账号和环境搭建也很费事。

构建方式

03真实使用日志

做法：从产品里真实用户和 agent 的交互中取数据。好处是分布最真实；难处在隐私、授权，以及日志里没有「对错」标签。

能查到的

  • Clio（2024-12，Anthropic）：一个保护隐私的系统，用来分析 Claude 的真实使用情况。它做的是使用分析，不是训练数据生产。
  • 前沿实验室是否、以及如何把真实 agent 使用日志用于训练：未公开。

对 PM 的意义：日志最大的用处往往不是直接训练，而是告诉你该造哪些任务：真实分布里哪些任务多、哪些失败多，再回到合成或人工去补。

构建方式

04反向合成与探索

做法：不先写任务。让 agent 在环境里探索、点来点去，再根据它实际走过的路径倒推出一个任务描述。这样任务和轨迹天然对得上，而且覆盖的是环境里真实存在的功能。

代表工作

  • OS-Genesis（2024-12）：先交互、后推任务，再用轨迹奖励模型筛质量。
  • Learn-by-interact（2025-01）：基于文档合成交互，再把交互历史总结成指令，叫 backward construction。在 SWE-bench、WebArena、OSWorld、Spider2-V 上，训练 Codestral-22B 最多提升 19.5%；反向构建这一步本身贡献最多 14.0%。
  • Explorer（2025-02）：9.4 万+ 条成功的多模态网页轨迹，4.9 万个 URL、72 万张截图；每条成功轨迹平均约 0.28 美元。
  • AgentTrek（2024-12）：先从网上抓教程类文本，转成带步骤的任务，再让 VLM agent 在真实环境里执行，VLM 评估器判对错。每条高质量轨迹 0.55 美元，不需要人工标注。

坑：倒推出的任务往往偏简单、偏「功能演示」，和真实用户的复杂意图有差距；环境本身的覆盖面决定上限。

构建方式

05蓝图 + 模拟用户

做法：多轮、带用户的任务（客服、订票、个人助理）光有 agent 不够，还需要一个「用户」。先由 pipeline 生成任务蓝图，写清用户目标和标准动作序列，再让一个 LLM 扮演用户、一个扮演 agent，把对话跑出来。最后对照蓝图验证。

代表工作

  • APIGen-MT（2025-04，Salesforce）：两阶段。第一阶段生成带 ground-truth 动作的蓝图，由 LLM 评审委员会审核、迭代；第二阶段通过模拟人机互动生成完整轨迹。训练的 xLAM-2-fc-r（1B–70B）在 τ-bench 和 BFCL 上超过 GPT-4o 和 Claude 3.5。开源 5K 条轨迹。
  • ToolACE（2024-09，略早于本页时间窗，作为基线收录）：自演化出 26,507 个 API，多 agent 互动生成对话，规则加模型双层校验。
  • Kimi K2：同样用 LLM 生成的用户画像跑多轮轨迹，见上一节。

和交互性数据的关系：这是你说的「交互性数据」里最可规模化的一种。核心资产是可信的用户模拟器，不是单条对话。

坑：模拟用户太配合、太会说话，和真实用户差距大；蓝图写死了标准答案，会惩罚其他合理的做法。

构建方式

06修复与改写

做法：模型学不会纠错，是因为训练数据里几乎全是一次做对的轨迹。于是把失败轨迹拿来，找到第一个出错的步骤，接上正确的后续，或者插入「发现错误、反思、改正」的片段。

代表工作

  • Agent-R（2025-01，字节）：用 MCTS 搜出正确和错误路径，由模型自己找到失败轨迹里第一个出错步骤，再拼接上同一父节点下的正确路径，迭代自训练。
  • AgentRefine（2025-01）：观察到已有 agent 训练数据在训练过的环境上表现好，换到没见过的环境就不行，而且会反复犯同一个错。做法是合成多样环境，让强模型根据环境反馈改正错误动作，泛化明显更好。
  • UI-TARS（2025-01，字节）：在推理中加入任务分解、反思、里程碑识别等模式，并迭代收集带反思的在线轨迹。
  • OpenCUA：给人工示范补「反思式长思维链」，也属于这一类。

坑：人为插入的错误如果不像模型真会犯的错，学到的是表演式反思。

构建方式

07步骤级标注

做法：不只判最后成没成，而是对每一步打标签：这步对不对、犯了哪类错。可以人工标，也可以用 Monte Carlo rollout 自动估计每一步的价值。

代表工作

  • TRAIL（2025-05，Patronus AI）：定义了 agent 错误类型的分类体系，人工标注 148 条长轨迹，覆盖单 agent 和多 agent 系统。最强的 Gemini-2.5-pro 在定位错误上只有 11%。
  • AgentPRM（2025-02）：用 Monte Carlo rollout 算每一步的奖励目标，训练过程奖励模型；另提出 InversePRM，直接从示范中学过程奖励。在 ALFWorld 上，3B 模型超过 GPT-4o 基线。

成本：步骤级人工标注的单价，以上论文都没有公开。可以确定的是长轨迹的人工审读很慢，TRAIL 只标了 148 条。

关系

08轨迹与评测

轨迹数据和评测是同一批东西的两面：拿去训练是数据，留出来打分就是评测。

  • 从只看结果到看过程：Agent-as-a-Judge（2024-10）用 agent 检查 agent 的中间过程，在 DevAI（55 个任务、365 条分层需求）上明显好于 LLM-as-a-Judge，可靠程度和人工基线相当。
  • LLM 判官本身要被评测：AgentRewardBench（2025-04）有 1,302 条网页 agent 轨迹，每条由专家判断是否成功、有无副作用、是否重复。12 个 LLM 判官里没有一个在所有 benchmark 上都最好；规则判分会低估成功率。
  • rubric 判分：Mind2Web 2 为每道题构建树状 rubric 的判官 agent，同时检查答案对错和来源引用。
  • 找错比判对错更难：TRAIL 显示，在长轨迹里定位错误，最强模型也只有 11%。
  • 失败模式分析：SWE-Bench Pro（Scale AI）对收集到的 agent 轨迹做失败模式聚类。

对评测 PM 来说，过程评测要回答三个问题：成没成（结果）、过程有没有副作用（比如删了不该删的、泄露了隐私）、是不是低效（反复绕圈）。最后两个只能从轨迹里看。

关系

09和三类数据的关系

轨迹不是第四类数据，而是三类数据在 agent 场景下的共同载体：

你的分类 轨迹形态 主要构建方式
专家数据 专家亲手做的示范；专家写的 rubric 用来过滤和判分 人工示范、rubric 过滤
复杂推理和知识数据 多跳搜索、长程推理的过程 知识图谱或混淆造题，再 rollout + 过滤（WebSailor、WebShaper）
交互性数据 多轮人机对话 + 工具调用 蓝图 + 模拟用户（APIGen-MT、Kimi K2）

可以把它理解成：前面三类决定「题」从哪来，轨迹决定「解题过程」从哪来。很多 pipeline 是先用三类方法之一造任务，再用 rollout 生产轨迹。

还有一个通用的工程问题：格式不统一。Agent Data Protocol（2025-10）把 13 个已有 agent 数据集统一成一种格式，SFT 后相对基座平均提升约 20%。它的观点是瓶颈不是数据源太少，而是格式太碎。

11什么稀缺

根据上面的论文，可以确定的几点：

  1. 便宜的轨迹不稀缺。合成方法已经把单条成本压到几毛钱（Explorer 约 0.28 美元，AgentTrek 0.55 美元）。
  2. 稀缺的是可信的判官。rollout + 过滤的质量取决于判官，而 AgentRewardBench 和 TRAIL 都显示 LLM 判官还不可靠。专家写的 rubric 和步骤级错误标注有价值。
  3. 稀缺的是真实分布。合成和反向构建的任务偏简单、偏功能演示；真实用户的复杂、模糊意图，只能来自人工示范或真实日志。
  4. 稀缺的是纠错数据。只有成功轨迹的数据会让模型不会从错误中恢复（Agent-R、AgentRefine 的出发点）。
  5. 稀缺的是可信的模拟用户。交互类轨迹能否规模化，取决于模拟用户像不像真人。

12面试谈资

  • 一句话框架：轨迹不是第四类数据，而是三类数据在 agent 场景的载体：题从专家、知识合成或交互中来，过程靠 rollout、示范或修复产出，质量由判官把关。
  • 数据公司的价值在判官和真实性，而不是条数。合成轨迹已经很便宜，客户买单的理由是「你的判官比我自己的准」，以及「你的任务比我合成的更像真实用户」。
  • 过程评测是评测 PM 的增量。结果评测已经成熟，副作用、低效、隐私越界只能从轨迹看。AgentRewardBench 的三个问题（成功、副作用、重复）可以直接用作框架。
  • 个人 agent 方向：主动性、长程记忆、discretion 都是过程属性，最终结果对了不代表过程得体。这类评测需要「模拟用户 + 轨迹级 rubric」，正好连接交互性数据和过程评测。
  • 可以主动问面试官的问题：你们交付的是轨迹、环境还是判官？客户怎么验收轨迹质量？纠错类数据是怎么造的？
